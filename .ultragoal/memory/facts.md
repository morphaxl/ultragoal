## Current understanding

- Product positioning is PREMIUM, results-first: never let token cost limit pursuing bold mechanisms — the answer to cost is a communicative UX, not restraint. Tell users up front, in rough terms, what a run will consume — in units the loop actually counts (turns, subagent dispatches), NEVER wall-clock estimates, which agents are reliably bad at — state costs honestly at the point of choice, then pursue the strongest result. Don't anti-sell expensive modes ("overkill", "right economics" hedging) — users who want ultragoal want the delta. THE BOUND on boldness is ROI, not budget: the multiple-of-vanilla token spend must buy measurable delta (solve rate, reliability, caught defects). FOURTH refinement (final word, same day): SIMPLICITY of the original version is a core product value — cut bloat and overengineering by judgment, validated by the existing test suite, NOT by live self-measurement experiments (a single bench arm-run costs ~1.2M tokens; owner stopped the cost-ratchet experiment mid-baseline). - Budget design, settled after a full round-trip (turns → tokens → back): the gate budgets in TURNS because a turn is the gate's own unfakeable event — a blocked stop — counted with zero parsing; token enforcement was built, then rejected for unreliability (see next entry). The user-facing dial is a named DEPTH TIER — quick pass (~10) / standard (25) / deep (60+) — never a raw number, same split as the API's `effort` parameter replacing `budget_tokens`. Token spend stays an OFFLINE measurement tool (transcript decomposition, the established pattern), per the owner: "useful for our own measurement... but not really" the loop's bound. - The harness scales to model strength via the `rigor` config knob: vanilla (default, strong models — the lean single-grader loop) / standard (single grader + interim re-checks + double-runs + scouts + log monitor) / max (3-lens PANEL verification `verify: panel` + every-claim cadence + multi-modal sweeps + deep interview, for weaker models or release stakes). - Transcript token counting is unreliable for in-gate use: usage objects are duplicated across JSONL lines (one line per content block — measured 757 usage lines vs 283 distinct message ids ≈ 2.7× over-count), the `<sid>/subagents/agent-*.jsonl` layout is undocumented internals, and resume//clear/compaction all reset or mutate the file. Naive `grep "output_tokens" | sum` is therefore only good for RELATIVE comparisons with itself. For honest absolute numbers, dedupe by message id first. Cache reads are ~95% of processed volume (487M of 510M in one heavy session), so "tokens processed" is dominated by the cheapest token class — compare costs on output tokens. [VERIFIED S8 · measured live transcripts · 2026-06-12]
